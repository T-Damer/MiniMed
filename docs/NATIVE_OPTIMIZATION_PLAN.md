# План оптимизации Android, WASM и WebGPU

Дата: 5 сентября 2026. Репозиторий: MiniMed, текущая версия при подготовке — 0.6.32.
Статус: **план, реализация не начата**. Исполнитель работает самостоятельно, без subagents.

## 1. Задача и границы

Уменьшить пиковую память, время открытия данных и длительность тяжёлых операций на Android.
Сохранить рабочий браузерный вариант, точность поиска, исходные документы и офлайн-доступ.
Сначала исправить перемещение файлов и владение базами; затем экспериментировать с ускорителями.

Не переписывать интерфейс на Compose, весь MedicalCore на Rust/C++, поисковое ранжирование на GPU.
Не подключать облачный backend, телеметрию или новую генеративную модель. Не менять клинические
пороги, определения, интерпретации ЭКГ и содержимое корпусов ради прохождения тестов скорости.
Не переносить пациентское хранилище в общий каталог контента.

Первые обязательные результаты: измерения, потоковое обновление APK, проект контракта файловых
артефактов. Остальные этапы имеют отдельные условия входа. Не реализовывать весь документ одним
большим изменением.

   поверх них старые версии файлов, не делать массовое форматирование.
3. Выполнять этапы последовательно. Перед каждым этапом перечитать его реальные файлы и callers:
   имена и структура могли измениться после создания плана.
4. До правки записать в отчёте: воспроизводимый сценарий, исходный результат, файлы изменения,
   проверку, которая отличит исправление от прежнего поведения.
5. После этапа выполнить его узкие проверки. Сохранить фактические результаты, затем переходить

6. Не ждать одобрения на обычные обратимые правки в разрешённом этапе. Если изменение нарушает

7. Не создавать новые задачи и не привлекать subagents. Не коммитить и не публиковать без запроса.
8. В конце обновлять CURRENT_STATE.md только реализованным поведением и проверенными цифрами.

## 3. Что подтверждено чтением кода

| Участок | Фактическое состояние | Следствие для плана |
|---|---|---|
| Обновление APK | state/native-update.ts получает целое тело через CapacitorHttp, затем кодирует части в base64 и отправляет в Android | Устранить весь круг Native → JS → Native для файла |
| Android updater | LocalMedUpdatePlugin.kt дописывает base64-фрагменты, открывая FileOutputStream для каждого | Загрузчик должен сам владеть потоком и файлом |
| Нативный SQLite | LocalMedDatabasePlugin.java хранит одно поле database и databaseLock | Для нескольких пакетов недостаточно создать второй TS store |
| TS SQLite adapter | capacitor-medical-store.ts хранит одну session на plugin и отвергает другую базу | Нужна согласованная модель владения с нативной стороной |
| Установка модулей | core/content-module-installer.ts требует Uint8Array, хеширует его, хранит bytesByArtifact; validator тоже получает bytes | Файловый downloader нельзя подключить одной заменой функции |
| Browser module runtime | Сохраняет bytes/sourceAssets в IndexedDB; чтение копирует ArrayBuffer, большие базы открывает через OPFS | Android нужен файловый backend; браузерный путь сохранить |
| ЭКГ | ecg-model.worker.ts задаёт WASM и numThreads = 1 | Подходит для отдельного сравнения потоков и WebGPU |
| Речь | asr.worker.ts использует Transformers pipeline, Whisper q8, блоки по 30 секунд | Не менять одновременно backend, модель и разбиение аудио |
| DICOM | dicom-runtime.ts уже использует WASM-кодеки, ограничивает количество workers | Начать с измерений декодирования/кешей, не писать новый viewer |
| Native vector search | Java проходит все векторы, сохраняет все hits и сортирует | При активном векторном корпусе сначала ограниченный top-k, затем SIMD/ANN |
| Android build | minSdk 24, targetSdk 36, arm64-v8a, NDK 27.3.13750724; native llama backend без GPU | Не считать WebGPU/NPU обязательной возможностью всех устройств |

Существующий native plugin для iOS: apps/app/ios/App/App/LocalMedDatabasePlugin.swift.
Общий TS-контракт нельзя поменять так, чтобы существующие вызовы iOS перестали работать.

## N1. APK скачивается непосредственно в Android-файл

**Читать и менять:**

- apps/app/src/state/app-update.ts и app-update.test.ts;
- apps/app/src/app/use-app-session.ts — только вызов updater и обработка прогресса;

- MainActivity.java — только если требуется регистрация нового plugin;
- apps/app/android/app/src/test/ — предлагаемые тесты потокового загрузчика.

Не добавлять универсальную систему задач на этом этапе. Расширить существующий updater.
Основную файловую/HTTP-логику отделить от PluginCall настолько, чтобы проверить её локальными
JUnit-тестами. Использовать платформенный HTTP-клиент, если существующий стек не даёт готового.

Предлагаемый смысл контракта, окончательные типы зафиксировать до правки callers:

```ts
type ApkTaskState = 'downloading' | 'verifying' | 'ready' | 'failed' | 'cancelled';
// start -> taskId; status/cancel работают по taskId.
// Событие: taskId, state, downloadedBytes, totalBytes: number | null, errorCode?.
// install(taskId) допускается только для проверенного ready-файла.
// Ни ArrayBuffer/base64, ни произвольный путь из UI через мост не передаются.
```

Шаги:

1. Проследить получение GitHub release asset. Сейчас код выбирает URL APK; не предполагать,
   что доверенный expectedSha256 уже передаётся. Проверить наличие digest/sidecar у реального
   процесса публикации. Вычисленный после загрузки хеш сам по себе не подтверждает ожидаемый файл.
2. Сохранить действующую поддержку релизов без digest. Если expected digest доступен — проверять
   его; если нет — не заявлять checksum verification как реализованную защиту. Обязательность
   digest для всех релизов требует отдельно согласованного изменения release-контракта.
3. Нативно валидировать HTTPS URL, переходы редиректов и целевой каталог. GitHub release downloads
   используют редиректы: не запрещать их все. Запретить переход на http/file/content URL.
   Имя локального файла генерировать в приложении, не брать напрямую из URL/заголовка.
4. Скачать поток в app-private .part с ограниченным буфером, например 64 KiB. Считать SHA-256
   во время записи. Проверить известный размер, ошибки записи и нехватку места.
5. Не трогать предыдущий готовый файл до успешной проверки нового. Закрыть потоки; выполнить
   атомарное переименование в пределах одной файловой системы.
6. Прогресс отправлять с ограничением частоты, например не чаще 4 раз в секунду и при смене
   состояния. Неизвестный total отображать неопределённым индикатором, а не фальшивыми 100%.
7. Installer запускать только отдельным пользовательским действием в foreground. Сохранить
   FileProvider и системную проверку подписи Android; не пытаться тихо устанавливать APK.
8. Перевести installAndroidApk/caller на task status. Подписку снимать при уничтожении view;
   при возвращении получать snapshot задачи, чтобы не зависеть только от пропущенных событий.
9. Удалить заменённые encode/split/write функции и тесты лишь после проверки всех callers.
   Не отключать глобально ограничения сети и не включать глобальный CapacitorHttp patch.
10. Проверить прежнюю очистку service worker/CacheStorage: её момент не должен уничтожать
    рабочее офлайн-состояние при неудачной загрузке. Любое изменение поведения описать явно.

**Проверки:** успешная загрузка; неизвестная длина; разрыв соединения; HTTP 404/500; редирект;
неверный digest при его наличии; неверный размер; отмена; недостаток места; повторное нажатие;
два конкурирующих запроса. Для сетевых тестов — управляемый локальный сервер, без скачивания
реального release на каждом unit test.

**Готово:** APK никогда не материализуется целиком в JS; UI показывает реальные этапы; старый
готовый файл сохраняется при ошибке; установка запускается только после ready. Сравнить память
для двух размеров файла: рост буфера приложения не должен быть пропорционален размеру APK.

## N2. Фоновая работа, resume и восстановление

**Файлы:** updater из N1; apps/app/android/app/src/main/AndroidManifest.xml;
при необходимости новый Android service/job и запись состояния задачи в app-private каталоге.
Не затрагивать storage/medical retrieval.

Перед реализацией сверить текущие Android SDK правила по официальной документации. minSdk=24:
нельзя написать только API 34+ ветку. Для длительного пользовательского скачивания оценить UIDT
на поддерживаемых ОС; для более старых — допустимый foreground механизм. Выбрать один вариант
для каждой группы ОС и объяснить выбор, а не реализовывать WorkManager, service и JobScheduler
одновременно «на будущее». Новая зависимость требует доказанной необходимости.

Шаги и правила resume:

1. Персистентно хранить taskId, идентичность артефакта, ожидаемый digest/размер, число записанных
   байтов, ETag/Last-Modified если доступны, состояние. URL с временными параметрами не логировать.
2. Перед retry завершить запись и закрыть файл. Offset брать из фактического файла, не из UI.
3. Отправлять Range и подходящий If-Range. При 206 проверять Content-Range и совпадение offset.
   При 200 вместо 206 начинать заново с усечением файла; никогда не дописывать полный ответ.
4. При 416 не объявлять успех автоматически: сверить ожидаемый размер и checksum, иначе перезапуск.
   При смене версии/validator не объединять байты разных артефактов.
5. SHA-256 resumed-файла проверять по всему файлу. Не считать digest только скачанного хвоста.
6. Retry использовать для временных ошибок с ограниченным backoff. Отмена — окончательное
   пользовательское действие, не повод для автоматического рестарта. Политику частичного файла
   на cancel определить явно; ошибка процесса и пользовательская отмена — разные состояния.
7. После process death восстановить запись и .part. Старое «downloading» без живого worker
   перевести в корректное состояние восстановления, не показывать вечную загрузку.
8. Добавить системное уведомление с прогрессом и отменой, если выбранный Android API требует его.
   После фонового завершения не открывать installer поверх другого приложения.

**Проверки на Android:** свернуть приложение; выключить экран; временно отключить сеть; уничтожить
процесс и снова открыть; отменить из уведомления; сервер игнорирует Range; артефакт сменился.
Force-stop пользователем тестировать отдельно: не обещать работу в обход системного force-stop.

**Готово:** возобновление не портит файл, состояние переживает перезапуск, повторная подписка UI
работает. Задокументировать ограничения ОС, которые код не может устранить.

## N3. Контракт файлового артефакта вместо обязательного Uint8Array

**Читать:** packages/core/src/content-module-installer.ts,
packages/core/tests/content-module-installer.test.ts,
packages/contracts/src/content-modules.ts,
apps/app/src/features/modules/browser-module-runtime.ts и его тесты,
apps/app/src/features/network/download-retry.ts, resumable-download.ts.

Это архитектурный этап перед интеграцией, а не механическая замена return type. Сейчас сам core
вычисляет SHA-256 по bytes, backend.stage принимает bytes, validator.validate принимает bytes.

1. Описать конкретный контракт двух представлений артефакта: browser bytes и непрозрачный
   staged-file token. Token выдаётся доверенным адаптером; не является произвольным OS-путём.
2. Указать, кто скачивает, проверяет размер/digest, владеет временным файлом и удаляет его.
   Проверка должна предшествовать активации. Простого поля verified=true от UI недостаточно.
3. Оставить единый ContentModuleInstaller с прежними состояниями/rollback. Не создавать второй
   независимый Android installer с другой семантикой ошибок и membership.
4. Обновить downloader, stage и validator согласованно. Browser adapter сохраняет проверку bytes;
   native adapter проверяет реальный файл и открывает именно его для SQLite validation.
5. Сохранить sourceSetDigest, точную принадлежность документов index artifact и исходные anchors.
   Ни файловый token, ни факт установки модуля не заменяют проверку membership.
6. Зафиксировать стратегию существующих IndexedDB установок на Android: безопасное чтение старого
   формата до проверенной миграции или явная миграция с сохранением старой копии. Не объявлять их
   пустыми и не заставлять скачивать всё заново без согласованного решения о совместимости.
7. Для API/персистентных изменений подготовить ADR с точными before/after формами и планом
   восстановления. Согласовать требуемую совместимость по AGENTS.md до зависимой реализации.

**Готово:** обе реализации проходят общие тесты успешной установки, неверного хеша, невалидной
базы, отсутствующего target document, отмены и rollback. Core не импортирует Capacitor/Java/SQL.
Ни один native file adapter не перечитывает файл в Uint8Array, чтобы удовлетворить старый validator.

   свободный путь из JS. Связать handle с версией пакета.
3. В Java заменить единственную database на ограниченный реестр соединений. Начать с одной
   последовательной очереди операций для корректности; отдельные очереди добавлять только по
   измерениям. SQL whitelist/read-only opening и проверки размера аргументов сохраняются.
4. В TS заменить единственную session на сессии по ключу редакции. Сохранить reference counting;
   close одного store не должен закрывать другие. Повторное открытие той же редакции переиспользует
   корректную сессию, а не создаёт лишнюю копию.
5. Операции открытия/копирования/quick_check выполнять вне UI thread. При таймауте JS нативная
   операция не должна незаметно завершиться позже и заменить уже выбранную базу: обеспечить
   отмену или изоляцию результата по request/task id.
6. Сначала оставить системный SQLite и имеющийся FTS5 probe. Если реальный набор устройств
   показывает несовместимость, отдельным изменением оценить bundled SQLite и повторить корпусные
   тесты. Не менять драйвер одновременно с multi-pack контрактом.
7. Согласовать iOS: сохранить его существующий путь через явную возможность backend либо
   реализовать такой же handle contract и проверить Swift. Не вызывать Android-only API на iOS.
8. При обновлении пакета дождаться освобождения старых читателей, активировать новую редакцию
   атомарно; не переименовывать файл под живым соединением без доказанной модели владения.

**Проверки:** core+A+B одновременно; запросы возвращают данные нужного пакета; закрытие A не
ломает B; reload; повторный open; неизвестный/закрытый handle; невалидный token; FTS5 отсутствует;
ошибка нового пакета оставляет старый доступным; результат поиска и anchor совпадают с WASM.

**Готово:** приложение реально использует несколько native stores, а не только новый plugin API.
Не утверждать улучшение поиска только по факту перехода с WASM на Java/native SQLite.

## N5. Первый файловый контентный модуль end-to-end

**Файлы:** installer/adapter из N3, SQLite из N4,
apps/app/src/features/modules/browser-module-runtime.ts, module-runtime-service.ts,
apps/app/src/features/modules/module-pointer-install.ts и тесты. Предлагаемый новый файл:
apps/app/src/features/modules/native-module-runtime.ts — только если требуется отдельный адаптер.

1. Выбрать один существующий проверяемый модуль с реальным index artifact и известным digest.
   Использовать маленький fixture для unit tests и большой файл для memory qualification.
2. Android скачивает .part → проверяет → валидирует SQLite/schema/digest/membership → атомарно
   активирует редакцию. UI показывает transferring/verifying/installing отдельно.
3. В registry хранить компактные метаданные. SQLite и архивы оставлять файлами Android.
4. Открытие одной картинки из source-assets не должно читать весь большой ZIP в JS. Использовать
   доступ к конкретному ZIP entry нативно либо проверенное извлечение при установке. Проверять
   выход за каталог, symlinks, размеры распаковки и хеши. Не внедрять оба способа одновременно.
5. Обновление/удаление пакета согласовать с открытыми readers и rollback receipt. Не удалять
   прежнюю редакцию до подтверждения новой и освобождения её handles.
6. Сохранить web путь downloadWithRetry. Для native используйте тот же смысл retry/cancel из N2;
   не делать обход retry слоя через одноразовый fetch. Нативную реализацию и её границу описать
   в соответствующих документах вместо буквального переноса браузерных байтовых функций.
7. Пройти UI-сценарий: результат поиска-подсказка → загрузка → полный документ → нужный anchor →
   перезапуск без сети → тот же документ. Проверить удаление и повторную установку.

**Готово:** в WebView нет полного ArrayBuffer модуля; данные доступны после перезапуска;
проверки corpus membership и provenance не ослаблены. Модели ASR/LLM не переводить автоматически
на этот путь: их текущий runtime может требовать иной способ чтения весов.

## N6. WASM: потоки и передача буферов

**Файлы:** apps/app/src/features/calculators/ecg-model.worker.ts,
apps/app/src/features/asr/asr.worker.ts и asr.worker.test.ts;
apps/app/src/features/library/dicom-runtime.ts;
apps/app/src/composition/worker-opfs-medical-store.ts — только при подтверждённых лишних копиях.

1. Начать с ЭКГ, где numThreads=1 явно задан. Прогнать одну модель на одном входе с 1/2/4 потоками.
   Не менять dtype, веса, размер изображения и preprocessing в том же сравнении.
2. Проверить реальную поддержку WASM threads/SIMD. SharedArrayBuffer и cross-origin isolation
   проверять в целевой среде. Не назначать numThreads=4 вслепую и не заявлять, что SIMD включается
   произвольным флагом: проверить используемую сборку runtime.
3. Для web COOP/COEP проверять вместе с источниками ресурсов и deployment. Не ломать загрузку
   моделей/шрифтов/CORS ради формального crossOriginIsolated=true. При отсутствии поддержки — 1 поток.
4. Проверить postMessage: крупные одноразовые буферы передавать через transfer list, только когда
   отправителю они больше не нужны. Добавить проверку, что код не читает detached buffer.
5. Не увеличивать одновременно workers OCR/DICOM/ASR и внутренние потоки ONNX. Измерить конкуренцию
   с поиском и прокруткой; выбрать небольшой общий уровень параллелизма без нового scheduler.
6. Освобождать inference session/буферы при смене модели. Не запускать несколько одинаковых
   загрузок весов при повторном открытии view.

**Готово:** выбранный режим даёт повторяемую пользу; выходные данные не ухудшены; fallback
проверен. Если 1 поток лучше, оставить 1 и сохранить результат эксперимента.

## N7. WebGPU для одной модели

**Вход:** N6 измерен; в реальном APK получен рабочий GPU adapter. Наличие navigator.gpu или
работа демо в Chrome не считается прохождением проверки внутри WebView.

1. Прочитать документацию установленной ONNX Runtime/Transformers версии и проверить фактический
   набор операторов модели. Начать с ЭКГ; речь — отдельный эксперимент после результата.
2. Использовать поддерживаемый WebGPU import/EP внутри существующего worker. Не добавлять
   proxy-worker поверх уже существующего worker и не переносить inference на UI thread.
3. Проверить adapter, создание session и реальный inference. Записать неподдержанные операции,
   CPU fallback и потери GPU device. Не объявлять весь граф GPU-ускоренным по имени provider.
4. Сравнить cold start, warm inference, суммарную операцию с preprocessing/readback, память и нагрев.
   На GPU не передавать весь корпус документов: только входы конкретной модели.
5. При ошибке инициализации использовать WASM один раз, с понятной диагностикой. Не создавать
   бесконечный цикл GPU → WASM → GPU. При ошибке запроса сохранять отмену и requestId.
6. Сравнить результаты на фиксированном наборе ЭКГ: маски/координаты, оценку качества и итоговые
   категории. Допуск численной погрешности задать до сравнения; клинические пороги не ослаблять.
7. Критерий включения по умолчанию: заранее выбранная значимая выгода, например не менее 20%
   по медиане полной операции на целевой группе устройств, без провала качества/стабильности.
   Это предлагаемый критерий решения, не обещание ускорения. Если он не достигнут — не включать.

**Готово:** отчёт с таблицей WASM/WebGPU и устройствами; явное решение включить или оставить
WASM. В обоих случаях этап может считаться завершённым. Неподдерживаемые устройства работают.

## N8. Условные дальнейшие работы

Эти пункты не являются обязательной частью первых поставок.

### N8a. Native inference для речи/ЭКГ

Начинать, если N6/N7 показывают неприемлемую задержку или память на Android. Сначала сравнить
одну и ту же модель в browser runtime и выбранном native runtime. Изучить имеющийся native code
в apps/app/android/app/src/main/java/com/arm/aichat и LlamaInferencePlugin.kt, но не считать llama
автоматически пригодным для Whisper или ONNX segmentation.

Выбрать один runtime после проверки операторов, лицензии, arm64, размера APK и offline работы.
Использовать Kotlin/JNI только там, где это нужно библиотеке. Через мост — file token и результат,
не base64 аудио/изображения/тензоров. Для ASR сохранить русский язык, punctuation/нормализацию,
качество медицинских терминов и cancellation. Сравнивать RTF и ошибки распознавания на одном наборе.
NPU/GPU backend не включать автоматически по наличию Snapdragon: нужна проверка модели и устройства.

### N8b. Изображения, OCR, DICOM

Сначала определить дорогой этап: чтение файла, decode, resize, обработка, upload в GPU или render.
Использовать существующие WASM-кодеки и workers. Проверить лимиты кеша и освобождение ресурсов
при закрытии, при необходимости сделать небольшие превью. Не менять диагностические исходники
или интенсивности пикселей ради уменьшения размера. Thumbnail не заменяет оригинал для анализа.

Не заменять Tesseract на Android OCR без проверки русского языка и медицинских терминов.
Переносить декодирование нативно только при доказанном выигрыше и сохранении метаданных DICOM.
Кеш 3D/серий ограничивать по байтам; не загружать все кадры и все масштабы заранее.

### N8c. Векторный поиск

Сначала проверить наличие chunk_embeddings в реально используемой редакции. В исследованном
core их было 0, поэтому ускорение Java searchVectors сейчас не ускорит обычный поиск этого core.
Если векторный корпус активен: заменить хранение/полную сортировку всех hits на bounded top-k
с прежним deterministic tie-break; проверить равенство результатов. Только затем оценивать
SIMD/WASM/native extension или ANN. ANN требует отдельного порога recall и не должен ухудшать
поиск редких названий/точных кодов. GPU-перенос FTS5 и медицинских правил не планируется.

## 5. Команды и общий выпускной барьер

Перед командами использовать очищенную среду по AGENTS.md. Пример для JS/Python:

```sh
env -i HOME=/Users/d PATH=/Users/d/.bun/bin:/Users/d/.local/bin:/opt/homebrew/bin:/usr/bin:/bin bun run typecheck
```

Bun — версия из packageManager. Android-командам добавить только проверенные пути JAVA_HOME,
ANDROID_HOME/ANDROID_SDK_ROOT и нужный PATH; не наследовать release tokens/provider secrets.
Приведённые ниже команды запускать из указанной папки, не переписывая pinned Gradle/runtime.

Из корня, применимые общие проверки:

```sh
bun run check
bun run typecheck
bun run test
bun run build
bun run python:check
bun run benchmark:all
bun run native:source:check
```

Узкие JS-проверки запускать через bunx vitest run с путями изменённого участка. Для UI —
соответствующие Playwright specs после сборки. Private-corpus команды нужны только при изменении
его инструментов; этот план не требует перестройки медицинских SQLite/JSON пакетов.

Из apps/app/android после подготовки JS assets и проверки cap sync diff:

```sh
./gradlew :app:testDebugUnitTest :app:assembleDebug
./gradlew :app:connectedDebugAndroidTest
```

Второй вызов требует совместимого устройства/эмулятора; проект arm64-only. Не убирать ABI filter
ради теста на x86. Не публиковать и не подписывать production APK в рамках проверки.
Не выдавать native:source:check за Gradle build или физический Android тест.

Общий барьер:

- [ ] Поиск и reader работают без сети и без модели.
- [ ] Исходные результаты/anchors и точное membership сохранены.
- [ ] Ошибки скачивания/установки не уничтожают рабочую редакцию.
- [ ] Web/iOS не сломаны изменением общего контракта.
- [ ] Есть реальные замеры Android там, где заявляется Android-выигрыш.
- [ ] Есть отдельные cold/warm и memory результаты, известны устройство и корпус.
- [ ] Проверены отмена, повторный запуск и очистка handles/подписок/буферов.
- [ ] Нет новых логов с клиническими запросами, исходниками, пациентскими данными или секретами.

## 6. Формат передачи результата после каждого этапа

В output/native-performance/ хранить отчёты измерений без пользовательских данных. В ответе:

1. Этап и конкретное изменение поведения.
2. Изменённые файлы и важные контрактные решения.
3. Проверки: команда, pass/fail, что не проверено и почему.
4. До/после: устройство, корпус/модель, размер выборки, длительность, память, качество.
5. Следующий допустимый этап и его блокеры.

Если улучшение не подтверждено, написать это прямо. Не оставлять ненужную экспериментальную
ветку включённой по умолчанию. Не создавать постоянные настройки для каждой проверенной гипотезы.

## 7. Готовый стартовый запрос исполнителю

> в этой поставке. Сохраняй чужие изменения, не публикуй и не коммить. Начни с воспроизведения
> существующего пути скачивания APK и измерений памяти. Не меняй release-совместимость или
> персистентные данные без требуемого правилами согласования. Доведи разрешённый этап до проверок,
> обнови CURRENT_STATE.md фактическими результатами. Если нет Android-устройства, реализуй и
