# Performance of search and the reader — November 2026 (STATE PERF5)

Owner 2026-11-08: «Можно ещё ускорить приложение? При поиске, чтении особенно». Measured first, then
fixed by measured impact; every number below comes from the same script.

## How it was measured

- **Script:** `apps/app/e2e/perf-baseline.spec.ts` (probes in `perf-harness.ts`), tables by
  `scripts/perf-compare.ts`. Rerun:

  ```bash
  bun run build:app
  PERF_BASELINE=1 E2E_PORT=4291 PERF_OUT=playwright/perf-now.json bunx playwright test perf-baseline --workers=1
  bun scripts/perf-compare.ts playwright/perf-before.json playwright/perf-now.json
  ```

  `PERF_ONLY=startup,search,reader` picks scenarios, `PERF_THROTTLE` (default 4) the CPU slowdown,
  `PERF_REPEATS` (default 3) the app starts.
- **Build and data:** the production build (`vite preview`), the real 440 MB core in OPFS and the
  largest published documents: КР 814_1 «Ишемический инсульт и ТИА» (970 K characters, 170
  sections — the longest of the 774 КР), КР 714_2 «Пневмония» (63 sections), the longest drug
  instruction (Флуконазол Медисорб, 128 K characters, ЕСКЛП group + ГРЛС instructions installed through
  the drug pointer). The browser profile (`playwright/perf-profile`, 1.1 GB, ignored) is kept between
  runs, so later runs measure an app start with the data in place; search runs delete the saved
  answers first, so «first» is a real core search and «repeat» the saved copy.
- **Device:** Chromium headless shell 1234 (Playwright 1.62.1) as a phone: 390×844 at 2.75×, touch,
  CPU throttled 4× on an M2 Max. **Android WebView was not measured**: no emulator is installed on
  this Mac, and the owner's phone was not used. 4× CPU on the Mac is a proxy for a mid-range phone,
  not a phone measurement.
- **Typing:** 90 ms per character; timings are from the last `input` event (Playwright types
  Cyrillic with `insertText`, which sends no `keydown` — a first version of the script measured from
  the wrong event; those numbers are not used).
- **Noise:** other sessions loaded the machine (load average 30–60 during the first runs, 3–9 during
  the final ones). Before and after were therefore built side by side and run interleaved under the
  same load: start-up from two rounds of three app starts each, search and the reader from two more
  rounds with the final build; cells are means of the rounds.

## What was found and fixed (by impact)

1. **Start-up: the 10.5 MB release catalog loaded and validated before the first screen.**
   `DefinitionReferencePanel` imported `MODULE_CATALOG` directly; the bundler put it into the chunk
   the search screen loads at start, so the 10.5 MB catalog was fetched, compiled and zod-validated
   ahead of the reveal, although `use-app-session` already deferred it «until after the boot reveal».
   `SearchWorkspace` also asked for it in `onMount` (installed calculators), and `use-app-session`
   imported the personal-file OCR ingest (tesseract + pdf.js) statically.
   **Fix:** the dictionary panel is loaded when opened (`LazyDefinitionReferencePanel`, text lines
   while its code arrives), installed calculators are read after the reveal and an idle moment, the
   OCR ingest is imported after the reveal. **Effect:** JS before the first screen 16.5 → 5.5 MB,
   main-thread blocking before it 155 → 26 ms, first screen (boot reveal) 829 → 403 ms.
   `bun run --filter @localmed/app build`'s eager graph: 88 files / 3.45 MB → 86 / 3.0 MB.
2. **Search: the first query after a start built every index inside itself.** The document index,
   terminology index, alias expander and spelling vocabulary over ~20 000 documents (normalising
   every title and alias) were built lazily by the first `search` — ~0.6 s of main thread on the Mac,
   a 550 ms task at phone speed. **Fix:** `MedicalCore.warmUp()` builds them in pieces (one per task)
   once the first screen is revealed and the browser is idle, and again after a core reload; results
   never depend on it (`packages/core/tests/warm-up.test.ts`). **Effect:** first search after start
   final list 2.0 → 1.3 s, its longest task 553 → 193 ms. **Cost:** the JS heap holds these indexes
   from the start (+29 MB after GC), which it held after the first search anyway.
3. **Reader: every slice of a long document laid the whole page out twice.** Wide-table detection
   read `scrollWidth` of every new table in an animation frame (a forced layout of the grown page,
   including tables in sections the browser skips with `content-visibility`), and every table's
   IntersectionObserver fired its first report for tables far off screen. The reader chrome measured
   itself on every DOM mutation of the body inside a frame and re-set two custom properties on the
   page each time, which restyles the whole document. **Fix:** tables in skipped sections are not
   measured until their section renders or nears the screen (`checkVisibility`), widths and the
   chrome are read in the task after the frame (layout already done), the chrome's properties are
   written only when they change. **Effect (814_1):** all 170 sections mounted 2.9 → 2.5 s, reopen
   2.8 → 2.3 s, layouts 175 → 110, style recalculations 276 → 186; 714_2 0.63 → 0.56 s.
   **Moved cost:** a table is measured when it first comes near the screen, so a jump into the
   middle of 814_1 has one ~100 ms task instead of ~50 ms, and a fling through it spends 151 instead
   of 94 ms in layout (slow frames 12 → 15 of 529); ordinary reading scroll is unchanged
   (p50 8 ms, p95 9 ms).

Search marks (`minimed:search:queued/debounced/run/version/saved/core-start/core`, no query text) are
in `SearchWorkspace` for the harness.

## Checked and left as they are

- **Scroll listeners:** the scroll spy and the page number read layout once per frame, after
  FIX-BATCH1; what remains in a fling is the browser laying out sections as they enter the screen.
  Reading scroll: p50 8 ms, p95 9–17 ms, ≤ 2 slow frames in 240 on every document.
- **Markdown parsing:** clinical documents render from chunks, not one Markdown string; the parser
  worker (`markdown-parser.worker.ts`) is used for user documents. Nothing to move.
- **Debounce and cancellation:** search waits 500 ms after typing and ignores stale answers
  (`searchGeneration`); no query runs per keystroke.
- **SQLite:** the worker's own search calls take 0.1–0.6 s at 4× for these queries; the slowest
  multi-word query («лечение артериальной гипертензии у детей») issues 32 calls over four mounted
  stores. Not changed here (see next steps).
- **The sticky section path** (`ReaderSectionPath`) reads heading positions after each mutation of
  the page inside a frame (184 ms of `getBoundingClientRect` in the 814_1 open profile). Moving that
  read after the frame's layout, as for the chrome, removed the forced layout from the profile but
  not from the totals (814_1 mounted 2 537 ms → 2 545 ms, blocking 234 → 256 ms, two interleaved
  rounds each): the layout simply happened in the frame instead. Reverted, not shipped.
- **Fonts, service worker:** the boot surface paints at ~130 ms (FCP); fonts are not on the
  critical path; the e2e profile blocks the service worker, so its precache was not measured.

## Trades

- **FMT-AUDIT: correct lists cost background mounting on the longest КР.** The formatting audit
  ([formatting-audit-2026-11-08.md](formatting-audit-2026-11-08.md)) made the КР evidence lines and
  «Комментарии» paragraphs of their own: 814_1 has 623 → 1 236 paragraphs. Same script, `main`
  7e049c943 against the branch, three alternating rounds at 4× CPU: 814_1 all sections mounted
  2 550–2 700 → 3 270–3 280 ms (blocking 240–270 → 340–365), which undoes most of this work's gain
  there (2.9 → 2.5 s); 714_2 565–595 → 590–620 ms; the longest instruction 740–755 → 805–825 ms; first
  text unchanged, the budget passes. A build with only the old list rule mounts 814_1 in
  2 530–2 650 ms, so the cost is the paragraph count, not the text code (whose first pass was made as
  cheap as before). Body-wide `text-wrap: pretty` is about 150 ms of it (3 090–3 140 ms without it on
  reader paragraphs): an option for the owner, not changed. Getting the rest back is a task of its
  own: the reader's per-paragraph mount cost (`PERF_ONLY=reader` on 814_1), for instance one block per
  item holding its evidence lines — a design decision.

## Next steps (not done)

1. **Kept-alive readers hold their DOM.** Back on the start page after 814_1 the page still has
   48 000 DOM nodes (1 500 before), after the next document 60 000: a reader stays mounted after it is
   left (back returns with state intact). Bounding how many stay mounted would cap memory on long
   reading sessions; it changes back-navigation behaviour, so it needs the owner's decision.
2. **Android WebView numbers.** Install an emulator (or a CDP-attached debug build) and run the same
   script against it; the 4× CPU proxy may differ from a real WebView.
3. **Multi-word search on several stores:** 32 SQL calls per query; batching the branches per store
   into one worker call would cut queueing.
4. **`OverlayDialog`'s scroll indicator** (`components/OverlayDialog.tsx`, the reader's overlay bar)
   re-reads the page's `scrollHeight` while a long document mounts: 133 ms of the 814_1 open at 4×
   CPU in the final profile. UI-BATCH3's file at the time of this work; not touched.
5. **Wide tables without a layout read:** a CSS-only sticky header for wide tables would remove the
   jump/fling cost moved by fix 3.
