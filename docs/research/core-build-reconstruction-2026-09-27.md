# Core.db build: reconstruction, profiling, and the pilot-removal step — 2026-09-27

Continuation of `diagnosis-alias-ambiguity-2026-09-27.md`, which found the diagnosis-alias
fan-out bug (fixed, `catalog_module_builder.py::_map_reference_aliases`, commit `4cab924f`) but
could not reconstruct the missing merge step feeding `build-core-reference-pointers`, and
recommended reconstructing/scripting it before any rebuild. This note does that, profiles the
pipeline, and records a coordinator decision to also drop 15 public-pilot documents.

**Update: the reconstructed pipeline was run to completion on this machine** (see "Real
end-to-end run" below) — not just designed. It produced a real, integrity-checked, diagnosis-
alias-fixed, pilot-removed candidate core.db, though built from today's data (larger medication
ledger, no migration-006 curated definitions) rather than a byte-identical copy of the Sep 8
release.

Committed script: `scripts/build-core.mjs` (`bun run content:core:build`). It is hash-keyed and
incremental (an alias-only change reruns only the reference-pointers stage onward), and every
finding below comes from a real run of it on this machine, not from reading code alone.

## Stage 1 — reconstructed pipeline (high confidence, verified against the released core.db)

The composed `apps/app/public/content/core.db` (19,987 documents) is **not** one merge. It is
three independent pointer-generation tracks assembled by one final `medbase compose`:

| Track | Mechanism | Documents (released core.db) | Reproduced by this run |
| --- | --- | ---: | ---: |
| `reference` (krasotaimedicina + mkb) | `medbase compose --input diseases.db --input mkb.db` → `medbase build-core-reference-pointers --source <merged>` | 15,904 | **15,904** (exact) |
| `clinical` | `medbase build-core-catalog-pointers --family clinical --ledger official-clinical-coverage-ledger.json` | 744 | **744** (exact) |
| `medication` | `medbase build-core-catalog-pointers --family medication --ledger official-grls-coverage-ledger.json` | 3,324 | 38,815 (ledger has grown since the Sep 8 release — another agent is actively expanding GRLS coverage on this machine right now, see below) |
| public pilot (`content/pilot-rf`) | `medbase build content/pilot-rf` → merged as full documents (not pointers) at the final compose | 15 | 15 |

Verification method: `metadata_json.catalogFamily` on the 19,972 `core_catalog_pointer` rows in
the released core.db groups into exactly 15,904 / 3,324 / 744 — the split above was derived from
that grouping, then reproduced independently by running the reconstructed pipeline stage by
stage and comparing document counts, not the other way around.

Corrected misconceptions from the previous note:

- `build-core-reference-pointers` cannot accept clinical catalog modules as input. A real run
  that tried raised `unsupported source_type: clinical_recommendation_catalog_record`
  (`_REFERENCE_SOURCE_TYPES` only allows `medical_reference`/`rls_mkb_reference`/
  `krasotaimedicina_reference`). Clinical and medication pointers are generated by the unrelated
  `build-core-catalog-pointers` command straight from their coverage-ledger JSON — no compose,
  no compiled per-specialty `.db` needed for that track at all.
- The "migration 007" curated input is not an ambiguous GRLS snapshot as first guessed. Its
  `--prepared` directory is simply `content/pilot-rf` itself: the 8 `drug.rf.*`
  `official_registry_summary` files there already contain the migration's `NEW_LABEL` wording, so
  for a **from-scratch** rebuild (as opposed to patching an old artifact) this migration step is
  redundant — the current committed pilot files are already correct.
- Migration 006 (`clinical_definition_migration_006.py`, 194 pointer updates + curated
  definitions) and migration 008 (`sqlite_layout_migration_008.py`, superseded 64 KiB layout) are
  real, committed, but historical/one-off; `scripts/build-core.mjs` does not replay them. Instead
  it produces the current core-db-size-2026-09-24.md "adopted" layout (16 KiB pages,
  external-content FTS) directly, because `medbase compose`'s own staging database already
  initializes at `page_size=16384` and rebuilds FTS through the external-content path
  (`sqlite_composer.py::_open_staging_database`/`_rebuild_chunks_fts`) — no separate migration
  pass needed for a fresh build.

Not fully resolved: the medication ledger's growth (3,324 → 38,815) is very likely simply
because another agent's `grls-instruction-batch` work (observed running concurrently on this
machine, `data/build/grls-instructions-active-*`) has been steadily widening GRLS coverage since
the Sep 8 release, not a bug in this reconstruction — but that wasn't independently confirmed,
only inferred from timestamps and the concurrent process. Re-run `bun run content:core:build`
once that other agent's work is stable to get the true current medication pointer count.

## Stage 2 — profiling (real measurements, not estimates)

| Stage | Real timing | Notes |
| --- | ---: | --- |
| `medbase compose` (diseases.db 928 MB + mkb.db 1.5 GB → 1.9 GB merged) | 64.5 s | Bulk `INSERT...SELECT` (`sqlite_composer.py::_copy_rows`), one transaction per input, `page_size=16384`. **Not a bottleneck.** |
| `medbase build-core-catalog-pointers` (medication, ledger→markdown, 38,815 docs) | a few seconds | Pure ledger JSON → markdown text, no SQLite. |
| `medbase build` on 38,815 simple pointer docs (medication) | ~2.5 min (≈4 ms/doc) | No `knowledge.json` for this pack. |
| `medbase build` on 46-document clinical specialty module | 0.89 s incl. `uv` startup | Confirms per-module clinical builds are cheap; not a target for the coordinator's clean-pilot step to worry about. |
| `medbase build` on 15,904 reference-pointer docs | ≈10 min (≈38 ms/doc) | Slower per-document than the medication pointers despite a similar "simple pointer markdown" shape; not fully root-caused (see below). |
| `medbase build --input data/intermediate/rls-mkb` (the **real** mkb family build, 9,836 source documents, 176,852 chunks, `--lexical-only`) | **>10 min 25 s, killed without finishing** (real time 625.55 s to that point, still in the in-memory parse/knowledge phase, 0 bytes written to the output `.db` beyond the initial 303 KB schema) | **The measured bottleneck.** Single-threaded, holds the whole pack in memory (`builder.py::_load_content_pack`) before writing a single SQLite row. `data/intermediate/rls-mkb/knowledge.json` is 186 MB; `load_knowledge_modules` + `apply_search_projection` (`knowledge.py`/`knowledge_modules.py`) cross-reference every chunk against every knowledge entity/fact/relation in pure Python/Pydantic. |

Conclusion: **SQLite-level work (compose's bulk copy, `write_sqlite_pack`'s `executemany` +
`journal_mode=OFF`/`synchronous=OFF`/`cache_size=-262144`) is already well-tuned and is not where
hours go.** The evidence points at two, additive, single-threaded Python-side costs instead:

1. **Knowledge-module cross-referencing for packs that ship a `knowledge.json`** (confirmed:
   mkb's 186 MB file). This is the dominant, measured cost — over 10 minutes and climbing for
   under 10,000 documents, with memory (RSS) growing continuously rather than staying flat,
   consistent with an accumulating rather than a fixed-size per-document cost.
2. **Per-document pointer-markdown rendering + parsing at higher volume**, secondary but real:
   15,904 reference pointers took noticeably longer than 38,815 medication pointers despite a
   similar "flat pointer markdown, no knowledge.json" shape — not root-caused with a profiler in
   this session (see "Not done" below), but consistent with the richer per-document content
   (`classificationPath`, multi-part definitions, larger shared `aliases.yaml`) that reference
   pointers carry versus the flatter medication pointers.

Extrapolating: a full rebuild touches the *mkb* family (this cost), the *krasotaimedicina*
family (`diseases.db`, same code path, smaller `knowledge.json` if any — not profiled directly),
the two catalog-pointer tracks, and — per the historical file timestamps in `data/build/`
(`core-before-knowledge.db` Sep 4 23:51 → `core.db` Sep 8 02:47, i.e. spread over four days) —
probably several manual, restarted, ad hoc iterations rather than one clean run. That combination
plausibly explains "up to ~12 hours" without needing a single pathological stage.

## Stage 3 — optimization and the real end-to-end run

What **was** applied and verified: the reconstructed pipeline itself removes the ad hoc, manual,
multi-day migration chain (`core-before-knowledge.db` → ... → `core-opfs-pages.db`, 8+ full-file
copies across Sep 4–8) by producing the target layout directly in one `compose --compact` pass.

**Real end-to-end run** (`CORE_BUILD_VERSION=0.7.0-test1`, `bun run scripts/build-core.mjs
--force`, this session, 2026-09-27): every stage ran successfully end to end using today's real
`data/build/diseases.db`, `mkb.db`, coverage ledgers, and `content/pilot-rf`. Both candidate
databases pass `PRAGMA integrity_check` (`ok`) and `PRAGMA foreign_key_check` (0 rows), and both
use `page_size=16384` with the external-content `chunks_fts` (`prefix = '2 3'`) — the
core-db-size-2026-09-24.md "adopted" layout, produced directly rather than through a later
migration pass:

| Candidate | Path | Documents | sha256 |
| --- | --- | ---: | --- |
| Pilot-inclusive (equivalence build) | `data/build/core.0.7.0-test1.db` | 55,478 | `1c50a1cc…` |
| Pilot-removed (coordinator's target) | `data/build/core.0.7.0-test1.no-pilot.db` | 55,463 | `a588c0e3…` |

`data/build/core-pilot-removal-diff.json` confirms exactly the 15 expected document ids were
removed (7 `kr.rf.*` + 8 `drug.rf.*`, ORS included per the resolved exception below) and nothing
unexpected changed (`matchesExpectation: true`). A direct spot check of the alias fix: MKB code
`I67.9` (the ОНМК/"Хроническая ишемия" example from the original finding) now resolves to
*both* `core.catalog.pointer.reference.krasotaimedicina.disease...` (Хроническая ишемия головного
мозга) and `core.catalog.pointer.reference.rls.mkb.node.i67-9...` (the MKB code page itself),
each carrying its own alias list — the fan-out fix is live in this build, not just in the code.

Two things this run is **not**: a byte-identical reproduction of the Sep 8 release (the
medication ledger has grown to 38,815 records from another agent's concurrent GRLS work, so this
candidate has far more medication pointers than the released 3,324; migration 006's 194 curated
clinical definitions were not replayed, see Stage 1), and a *fast* run in absolute terms — see the
per-stage timing below, still dominated by Python-side per-document processing, not SQLite.

What was **not** done, and why, honestly:

- No cProfile-based root-cause of the knowledge-module cost was captured (the profiling run
  against the full `data/intermediate/rls-mkb` family was killed to free the shared machine after
  10+ minutes; a proper profile needs a dedicated, uncontended run). The fix this evidence points
  at — parallelize `_load_content_pack`'s per-document parsing across a process pool, and/or
  check whether `load_knowledge_modules`'s one-time `KnowledgeEntity.model_validate` pass over the
  full `knowledge.json` (rather than the per-document cross-referencing) is itself the dominant
  cost — was not implemented. Changing `tools/ingest`'s core builder for ordering-sensitive,
  ID-stable output (AGENTS.md: "Rebuilding unchanged input produces the same ordering, IDs,
  SQLite bytes... when `builtAt` is fixed") needs its own equivalence-proof pass and was out of
  scope for the time available here. The reference-pointers stage in the real run above (15,904
  simple pointer documents, no `knowledge.json`) itself took roughly 10 minutes — much slower
  per-document than the 38,815-document medication-pointer stage (~2.5 min) despite a similarly
  flat shape; this second, smaller anomaly is flagged but also not root-caused.
- `data/build/diseases.db`/`mkb.db` themselves were treated as pre-built inputs, not rebuilt from
  `data/raw`/`data/intermediate` in this run (that would hit the killed-after-10-minutes cost
  above). A true from-scratch timing of the *entire* chain, including those, still needs a
  dedicated long background run.
- `benchmark:lookup-quality`, `benchmark:doctor-lookup`, `benchmark:all`, `benchmark:pilot`, and
  `bun run verify` were **not run** against the new candidates — recommended next step now that a
  real candidate core.db exists.

## Coordinator decision (2026-09-27): drop 15 public-pilot documents, gated

Recorded verbatim intent: after the reconstructed pipeline proves equivalent to the released
core.db, remove the 15 `publicPilot: true` documents from `content/pilot-rf`
(7 `kr.rf.*` clinical-recommendation retellings + 8 `drug.rf.*` registry retellings) as a
**separate step with its own diff report**, via inputs/build — never by hand-editing a built
database — because each already has a real pointer from the reference/clinical/medication tracks
above. The oral-rehydration-salts (`drug.rf.oral-rehydration-salts.powder-18-9g`) retelling is
the one exception: drop it only once a real GRLS/ESKLP oral-rehydration-salts instruction has
actually landed in the medications package; otherwise keep it.

`scripts/build-core.mjs` implements this as `public-pilot-clean-build` → `finalize-clean` →
`pilot-removal-diff`, gated behind `finalize` (the pilot-inclusive, equivalence-proving build)
having already run. `pilot-removal-diff` writes `data/build/core-pilot-removal-diff.json`
(removed/kept document ids, checksums of both candidates, and the ORS decision with its
rationale).

ORS resolved (2026-09-27, coordinator confirmation): a real GRLS/ESKLP oral-rehydration-salts
instruction (Регидрон + 3 more) has landed in the medications package —
`data/build/medications-v2.db` and `data/build/grls-selected-instructions-v2.db` both carry
`drug.rf.regidron.instruction` ("Регидрон: инструкция по медицинскому применению"), built
2026-09-27 16:12/16:22, i.e. after and independent of the stale Sep 2/Jul 24 records first found
in this session; only their YAML registries are committed. `scripts/build-core.mjs` therefore
drops the pilot ORS document by default along with the other 14 (`--keep-ors` restores the old
conservative default). Since all 15 public-pilot documents are now dropped by default, the
coordinator noted `content/pilot-rf` and its build can be dropped from the core chain entirely
once this is the settled behavior; `public-pilot-build`/`finalize` (pilot-inclusive) are kept in
the script only to reproduce the *old* released core.db for the equivalence proof, not as the
target end state.
