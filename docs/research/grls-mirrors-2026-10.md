# Зеркала ГРЛС и другие хранилища официальных инструкций (2026-10-02)

Исследование без массовых загрузок: к ГРЛС сделано 6 запросов (robots.txt, два HEAD, один диапазонный GET на 1 КБ PDF — всё статика, без `.aspx`; плюс по одному HEAD/robots на алиасе `grls.minzdrav.gov.ru`), к Wayback — около 12 запросов к индексу CDX и 2 снимка, к Common Crawl — 5 запросов к индексу, к medi.ru — 31 страница. CAPTCHA не затрагивалась. Контекст: [GRLS_INGESTION_HANDOFF.md](../GRLS_INGESTION_HANDOFF.md) (раздел G1), [data-sources-2026-10.md](data-sources-2026-10.md), [grls-reuse-rights-2026.md](grls-reuse-rights-2026.md).

Обозначения: ✔ — проверено запросом в этой сессии; ○ — посчитано по данным репозитория; ◐ — по описанию/косвенно, не проверено.

## 1. Короткий вывод

1. **Полного зеркала ГРЛС с теми же официальными PDF нет.** Wayback хранит ≈0,3 % нужных документов (и только старые редакции), Common Crawl — ничего (уважает robots), на Hugging Face/Kaggle/GitHub готовых наборов инструкций ГРЛС нет; ближайшее — набор по РЛС (не ГРЛС, права под вопросом) и страницы medi.ru (дословный текст, но версии 2011–2017 гг.).
2. **URL PDF вывести из имеющихся данных нельзя**: имя файла содержит случайный GUID v4 (8 672 из 8 672 известных URL), а ни экспорт реестра, ни ЕСКЛП, ни наши ledger-записи GUID/`idReg`/`routingGuid` не содержат. Зато **сам файл — статика без CAPTCHA**: GET/HEAD/Range работают без cookie и Referer (✔). То есть узкое место — не скачивание, а *узнавание URL*, которое даёт только приложение `.aspx` (4 запроса из ~5 на регистрацию), и именно оно ставит CAPTCHA.
3. Реальные варианты — только официальные: запрос в НЦЭСМП/Минздрав (особенно по ЕАЭС-регистрациям: 6 415 из 8 325 недостающих — формат `ЛП-№(…)-(РГ-RU)`), коммерческий договор (РЛС Aurora), либо принять неполноту и добирать ГРЛС по приоритету под лимит CAPTCHA. Обходить CAPTCHA нельзя.

## 2. Формат URL инструкции и «один запрос на документ»

Как сейчас находится PDF (`tools/ingest/src/localmed_ingest/grls_collect.py`, `fetch_instruction`): GET `GRLS.aspx` (форма) → POST поиск по номеру РУ → из выдачи `routingGuid` → GET `Grls_View_v2.aspx?routingGuid=…` (карточка, в ней скрытое поле `hfIdReg`) → POST `GRLS_View_V2.aspx/AddInstrImg` с `{regNumber, idReg}` → ответ со ссылкой → GET PDF. Итого 4 запроса к `.aspx` + 1 к статике.

Разбор 8 935 известных `instructionUrl` из `data/build/grls-instructions-active-state.jsonl` (○):

| Шаблон | Кол-во | Что в нём |
|---|---|---|
| `/InstrImg/YYYY/MM/DD/<seq>/<GUID v4>.pdf` | 8 672 | дата загрузки, сквозной номер (281…1 535 141, с датой согласован не строго: 444 из 8 665 соседних пар нарушают порядок), случайный UUID v4 |
| `/InstrImg/YYYY/M/D/<seq>/<РУ>[год]_<n>.pdf` (без нулей в дате) | 263 | старый вид: РУ в имени, но дата и `<seq>` всё равно неизвестны |
| старый `/InstrImg/<10 цифр>/<РУ>[год]_<n>.pdf` | 0 в ledger; ~90 в Wayback | исторический вид до ~2021 |

Что есть в данных, чтобы построить URL заранее (✔/○):

- Экспорт реестра `grls-02.10.2026.zip` (8 XLSX): только поля реестра (номер РУ, даты, держатель, ТН, МНН, формы, НД…), **ни `idReg`, ни `routingGuid`, ни ссылок на документы** (✔ заголовки листов). `sourceWorkbook` и `officialUrl` в нашем каталоге — общий `GRLS.aspx`.
- ЕСКЛП (Excel-выгрузка 2.0.4; ✔ список колонок в `esklp_rows.py`): колонок со ссылками на инструкции нет. XML-схему 21.5 с корневым сертификатом Минцифры в этой сессии не вскрывали (по правилам NSI — только внутри контейнера); по S1 текстов инструкций там нет, ссылки на документы не подтверждены. Остаётся ◐.
- Ledger сохраняет `instructionUrl` только для успехов; `idReg`/`routingGuid` для неуспешных не фиксировались.
- GUID — UUID v4 (случайный), поэтому даже при известных дате и номере файл не угадать.

**Вывод:** сократить «5 запросов» до «1 запроса на документ» без обращения к `.aspx` нельзя. Но можно улучшить две вещи (в рамках текущих правил):

- Записывать при каждом успехе `idReg` и `routingGuid` (в ledger их сейчас нет). Тогда повторное получение URL (например, при обновлении инструкции) не потребует поиска (−2 запроса: GET формы и POST поиска) — ◐, не проверено, что `AddInstrImg` работает без предварительного GET карточки.
- Когда URL уже известен (обновление, повторная загрузка битого файла), качать только статику — 1 запрос, без риска CAPTCHA.

### Хост файлов

- `https://grls.rosminzdrav.ru/InstrImg/2025/09/03/1520951/80abe4c2-….pdf` (✔ 2026-10-02): `200`, `Content-Type: application/pdf`, `Accept-Ranges: bytes`, `ETag`, `Last-Modified`, **без `Set-Cookie`**, без Referer и сессии; диапазонный запрос `Range: bytes=0-1023` → `206`, тело начинается с `%PDF-1.6`. Тот же сервер, что и приложение (`Server: webserver`), но отдаёт файлы напрямую, CAPTCHA на статике не видна.
- `robots.txt` (✔; `Last-Modified: Tue, 19 Sep 2023`): помимо `Disallow: /` и `Disallow: *.aspx` для `User-agent: *` теперь явно перечислено `Disallow: /instrimg/` (для `*` и для Yandex) — то есть сам PDF-каталог тоже явно закрыт. Это дополняет раздел 3.2 data-sources-2026-10.md (там сказано только про `/`).
- Алиас `grls.minzdrav.gov.ru` (✔): A-запись `194.0.219.200`, как у `grls.rosminzdrav.ru`; тот же `robots.txt` (побайтно: 622 байта, тот же ETag) и тот же PDF (тот же ETag/длина). Это **алиас того же сервера, не зеркало**; для лимита CAPTCHA, вероятно, ничего не меняет (счётчик не проверялся; менять хост ради обхода лимита — не рекомендуется).
- CAPTCHA приходит в `.aspx` как `div#dCaptcha` с картинкой (`captcha-2026-10-02T054116Z.html`), поверх формы поиска; последний запуск остановился после 14 успехов в слабом режиме, общий лимит ≈140–220 запросов.

Грубая стоимость: 8 325 недостающих регистраций (без `ФС-`) × 4 запроса `.aspx` ≈ 33 тыс. запросов; при лимите ≈ 200 запросов до CAPTCHA это ≈ 40–50 регистраций за окно (○, по ledger/логу первого прогона и `progress.json`: 42,9 регистраций/час).

**Выборка 30 случайных недостающих регистраций** (seed 20261002; из 8 325 активных планируемых без `ФС-`, состав: 24 `ЛП-№(…)-(РГ-RU)`, 3 `ЛСР-`, 1 `ЛС-`, 1 `Р N…`, 1 `П N…`):

- Прямой поиск PDF по регистрации в архиве **невозможен**: PDF нового вида называются GUID, ключа «регистрация → URL» в архиве нет; страницы поиска ГРЛС — POST, не архивируются. Поэтому проверка сделана по полному списку 721 URL, а не 30 отдельными запросами: **0 из 30 найдено (0 %)**, как по номеру (старый вид с РУ в имени), так и по GUID.
- Распространение на все 8 325: по номеру совпало **27 регистраций (0,3 %)** — старые PDF формата `ЛП-00xxxx[год]_n.pdf` (2010–2016) для регистраций, которые потом переоформлены в `ЛП-№(…)-(РГ-RU)`; это **устаревшие редакции**, а не текущие инструкции.
- Карточки: снимок карточки (проверен один, 2025-06-02, 80 КБ) содержит `idReg` (`hfIdReg`), но **ссылки на PDF в нём нет** (она подгружается Ajax `AddInstrImg`), поэтому карточки в архиве URL PDF не раскрывают.

Итог: Wayback практически бесполезен для закрытия пробелов. Единственная мелкая выгода — 112 неизвестных GUID-PDF (≈1,3 % от 8 325, если все относятся к недостающим; вероятно меньше): их можно скачать из `web.archive.org` по адресам вида `/web/<ts>id_/<url>` (~112 файлов, ◐ объём ≈ 30–60 МБ), определив РУ по тексту; это не нагрузка на ГРЛС, но и не решение.

## 7. Рекомендованный план

1. **Не тратить время на зеркала**: Wayback/Common Crawl/другие хосты не дают текущих PDF. Единственная мелочь — 112 GUID-PDF из Wayback (по желанию, с привязкой по тексту).
2. **Адресный запрос в НЦЭСМП** (ФГБУ «НЦЭСМП» Минздрава России) на ОХЛП и листки-вкладыши по списку из ~6 400 ЕАЭС-регистраций (`ЛП-№(…)-(РГ-RU)`): приложить CSV (номер РУ, ТН, МНН, держатель) из плана 02.10.2026; цель — пакетная выдача PDF одним архивом. Параллельно подготовить текст заявки на доступ к БД ГРЛС (если владелец захочет повторить попытку по формальному каналу, ◐ в том числе запрос по 8-ФЗ).
3. **Сбор с ГРЛС — только по приоритету и в пределах лимита**: сортировать недостающие регистрации по пользе (ЖНВЛП, `По рецепту`, наличие АТХ-кода в ЕСКЛП, частота поиска), не по порядку. Один рабочий день ≈ одно окно до CAPTCHA (≈40–50 регистраций); 1 000 приоритетных регистраций ≈ 3–4 недели. Остановка на первой CAPTCHA, как в G1. Не использовать смену хоста, cookie и параллельные сессии, чтобы пройти лимит.
4. **Улучшить сборщик (мелкие правки, не сделаны)**: сохранять в ledger `idReg` и `routingGuid` у каждого успеха; при повторных скачиваниях/актуализации ходить только на статику (`instructionUrl`), без `.aspx`; проверить, что `AddInstrImg` работает без предварительного GET карточки (1 запрос на проверку).
5. **Бюджет/договор**: запросить условия РЛС Aurora для сравнения с трудозатратами; решать после ответа НЦЭСМП.
6. До получения PDF для остальных использовать как «справочник, не официальный текст» то, что уже решено в K1 (Allmed и т. п.), с бейджем; **не подставлять** medi.ru/РЛС-набор в качестве инструкции.
