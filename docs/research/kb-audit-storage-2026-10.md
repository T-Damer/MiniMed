### 2.2 (b) FTS при сжатом тексте

Внешний контент (как в ядре, view `chunks_fts_source`) + `UPDATE chunks SET normalized_text=''` после `rebuild`:
индекс не меняется (fts5vocab: 621 588 = 621 588 вхождений), `PRAGMA integrity_check` ok, top-50 по bm25 идентичен 60/60 (ЕСКЛП) и 100/100 (ядро). Побочный эффект: `INSERT INTO chunks_fts(chunks_fts,rank) VALUES('integrity-check',1)` после обнуления падает — rank-1 проверку надо делать до обнуления в сборщике. Запрос приложения читает только UNINDEXED-колонки и bm25 — snippet()/highlight() не используются (`sqlite-medical-store.ts` §search), так что contentless не нужен: достаточно внешнего контента, читатели не меняются. Размеры ЕСКЛП-resp: 93.05 → 77.60 (внешний) → 65.56 MB (+пустой normalized). `detail=column` ещё −44% FTS, но ломает фразовые запросы — не рекомендуется. SQLite в приложении 3.53 (sqlite-wasm).

Прототип «документ-блобы» (`doc_text(document_version_id, chunk_rowids, lens, body zstd+dict)`; kras): тело 128.4 → 23.9 MB, файл 629.8 → **306.3 MB**, zstd-19 всего файла 100.6 → 88.1 MB; открытие документа 0.104 ms (200 случайных). ЕСКЛП-cardio: текст 109.2 → 1.4 MB, metadata `smnnNodes` 78.5 → 1.6 MB, файл 339.6 → **52.6 MB** (остаётся FTS 33 MB, chunks 12.8). Рекомендуемая гранулярность — **фрейм ≤64 KB** по секциям (чанк хранит frame_id/offset/len): без словаря 64 KB-фреймы дают 4.4–4.8× против 5.1–5.9× целым документом (клинреки). Ограничения: ЕСКЛП обучен на пересекающихся документах (оптимистично); читатели `getChunks*`/гидрация поиска меняются; Android-путь (SQLCipher) не умеет UDF, поэтому разжимать надо в TS после выборки.

### 2.5 Пользовательские файлы и книги

Реальные файлы владельца (`Med/`, 12 GB: 548 PDF, 222 DOCX, 109 DOC, 66 PPTX…; сэмпл 20 штук/тип, zstd-3):
PDF **1.09×** (-19: 1.088), DOCX 1.02, PPTX 1.01, PPT 1.07, DjVu 1.00, JPG 1.04, PNG 1.01, DOC 1.48. Хранить исходные бинарники сжатыми бессмысленно.
Сжимать стоит **производное**: `pages` (текст страниц и `words` с боксами в IndexedDB, JSON), текстовые форматы (md/txt/html/fb2: 3.7–5.8× на корпусных текстах). OCR-слова не мерялись (нет образцов).

Предлагаемый формат `MZF1` (для текста и OCR-страниц): запись в IDB `{id, codec:'zstd'|'none', rawBytes, sha256, frameRaw:65536, dictId?, frames:[{off,len,rawLen}], blob}`; кодек выбирается пробой 256 KB (отношение <1.15 → `none`). API:

```ts
interface PackedStore {
  put(id, data: Blob|Uint8Array, hint: {mime}): Promise<void>;     // сжатие в воркере, без видимости пользователю
  open(id): Promise<PackedReader>;                                  // читает только таблицу фреймов
}
interface PackedReader {
  readRange(start, len): Promise<Uint8Array>;   // декодирует нужные фреймы, LRU 8 фреймов
  stream(from?): ReadableStream<Uint8Array>;    // первые страницы сразу, хвост — фоновой prefetch
  blob(): Promise<Blob>;                        // для PDF.js/epub.js, когда нужен целый файл
}
```
Первые страницы: 1-й фрейм 0.1–0.3 ms; остальное — фоном через `requestIdleCallback`. PDF хранить как есть и отдавать PDF.js диапазоны.

### 2.6 Позиция чтения

Сегодня: официальные документы — активная секция лишь в сигнале `activeAnchor` (`document-reader-chrome.tsx`), якорь в хэше только при входе по ссылке; цепочка (trail) в `sessionStorage` (теряется при убийстве процесса); `scrollByView` корневых вкладок — в памяти. Пользовательские документы: `UserLibraryDocument.lastOpenedAt` и `userLibraryProgressFraction` (= прогресс OCR, не чтения). Позиции нет — после перезагрузки документ открывается сверху. В нативной ветке `saveReaderSnapshot(route)` уже есть.

Нужно: хранилище `reading_positions` (IDB; ключ `documentId + versionId`) со значением `{anchor: стабильный chunk/section id, charOffset в чанке, scrollRatio как запасной, epubCfi | pdfPage+yRatio, contentChecksum, updatedAt}`; запись по `scrollend`/idle (debounce 400 ms) и синхронно в `localStorage` на `visibilitychange/pagehide` (WebView убивается без предупреждения); при смене версии — ремап по стабильному chunk id, иначе по секции; восстановление через уже существующий `initialAnchor`-путь `OfficialDocumentReader`. Оценка 3–5 дней.

## 3. Связи терминов

### 3.1 Как устроено сейчас

- Текст чанков **не содержит** разметки MiniMed-связей. Ссылки строятся при открытии: `buildDocumentLinkPhrases(availableDocuments)` + `createDocumentLinkMatcher` (`document-medication-links.ts`, вызывается в `OfficialDocumentReader`, `SearchWorkspace`, `DocumentText`). Источник фраз — заголовки/shortTitle/`navigationAliases` документов-указателей; превью — `metadata.canonicalDefinition`.
- Стоимость при каждом открытии (core, native SQLite, host): проекция навигационных документов 13.1 MB JSON, SQL ≈240 ms + parse ≈65 + фразы ≈100 + матчер ≈40 ≈ **450 ms** (на телефоне больше; не мерено); 31 362 фраз, 7 905 с превью (9.05 MB в памяти).
- В хранилище для связей: `canonicalDefinition` 10.76 + `definitionPreviewAnchor` 0.97 + `clinicalMedicationLinks` 1.12 + мёртвый `globalQueryAliases` 5.84 MB (метаданные ядра); `aliases` 27.6; `knowledge_document_links` 33.9 (19 972 «discovery-pointer» + 6 430 definition); `knowledge_evidence` 31.7; mkb: relations 27.2 + evidence 39.9 + `rlsMedicationPackaging` 10.5; defref: ключи/компактные ссылки ≈14.5 MB.
- В исходном тексте kras есть **192 790 markdown-гиперссылок** на сайт-источник (+14.75 MB URL, 11.5% текста). Они — исходный текст, должны остаться byte-exact; `parseDocumentText` распознаёт только `![]()`, т.е. в читателе они, судя по коду, выводятся как есть (в UI не проверялось).

### 3.2 Динамическая схема (измерено на реальных словарях)

Словарь: имена/алиасы/заголовки ядра + имена defref = **89 582 уникальных нормализованных фразы** (ё→е, lower), 49 314 слов, 242 055 узлов слов-trie.

| Формат | Размер |
|---|---:|
| Отсортированный массив фраз, raw / zstd-19 | 4 513 / **525 KB** |
| Front-coding (блок 16), raw / zstd-19 | 2 656 / 531 KB |
| Таблица слов + последовательности id слов, zstd | 622 KB |
| Привязка фраза→цели (varint-дельты), zstd | 196 KB |
| **Итого файл словаря** | ≈ **0.7 MB** (31k фраз текущего набора: 0.29 MB) |
| В памяти: Map-trie (слова интернированы) | ≈25 MB heap, сборка 87–120 ms (CSR на typed arrays — оценочно 3–4 MB) |

Скорость (V8, горячий, 1 поток; в Worker не меняется):

| Документ | Текущий матчер | Слов-trie, тот же набор 31k | Слов-trie, 89.6k |
|---|---:|---:|---:|

### 3.3 Что теряется и как сохранить точность

Если подключить **все** термины, шум огромен: на 307 MB (kras + клинреки) 1.72 млн совпадений, 90% от омонимов и общих слов («при» 217 554, «как», «лечение», «нет», «это»; 751 термин встречается в >2% документов; 21 730 из 90 088 фраз имеют ≥2 цели). Эвристика (одна цель, DF ≤2%, длина ≥4, короткие общие слова defref вырезать) оставляет 63 742 термина и 123 тыс. совпадений (0.40/KB, медиана 7 уникальных терминов на документ, p90 21).

Как сохранить точность: (1) стоп-лист и флаги `ambiguous`/`generic` считаются при сборке по DF корпуса; (2) неоднозначная фраза → лист альтернатив (`alternatives` в матчере уже есть), без автоссылки; (3) аббревиатуры — регистрозависимо (механизм `exactCase` уже есть); (4) ссылаться только на понятия типов disease/medication/classification/scale, слова defref — только по явному списку; (5) исключения по документам `link_exceptions(doc, start, end)` для отклонённых связей (`review_status='rejected'`); (6) опционально на сборке — предвычисленный набор терминов документа (≈0.2 MB на 6 812 документов; спаны ≈0.5 MB), тогда читатель ищет лишь десятки терминов; (7) определение — только по тапу (запрос по concept id в пак определений, у ядра остаётся 0.93 MB zstd на 6 430 текстов превью, если превью офлайн нужны всегда). Потеря: контекстная разрешённость омонимов (нужно ручное/ML-решение), лексическая разметка не привязана к смещению (но смещения стабильны, пока `original_text` byte-exact).

## 4. Ядро как индекс слов и понятий

Состав (измерено сборкой реального бинарника из core + mkb + defref): 

| Блок | raw KB | zstd-19 KB |
|---|---:|---:|
| id понятий (80 829, front-coded) | 1 353 | 644 |
| тип понятия | 81 | 6 |
| канонические названия (display) | 3 037 | 589 |
| модуль + id целевого документа | 873 | 151 |
| имена/алиасы (100 583 нормализованных, front-coded) | 3 171 | 578 |
| имя → понятия (постинги) | 509 | 313 |
| связи (76 186: classified-as 17 993, listed-on-rls-mkb-page 51 206, active-ingredient-of 6 986, …) | 381 | 130 |
| **Итого** | **9 400** | **≈2 400** (один поток 2.31 MB) |

Плюс ≈12k торговых названий ЕСКЛП и 7 181 бренд РЛС — ещё ≈0.3–0.5 MB. Для сравнения: сегодня 440.9 MB raw / 76.2 MB gz (÷190 / ÷32).

Содержимое: стабильный `concept id`, тип, каноническое имя, алиасы, указатели `(moduleId, targetDocumentId)`, связи (subject, predicate, object, status). Нет: чанков, секций, FTS по тексту, цитат/evidence, превью (они в модулях/паке определений).
Поиск: по имени (префикс/опечатки по отсортированному массиву или FST) → понятие → «что есть и где». Это заменяет `chunks_fts` (35 MB) и 57k чанков-указателей.
Как модули подключаются: `catalog.preview.json` уже хранит членство `documentTable` (id, версия, checksum, title) — те же данные, что указатели ядра дублируют; ядро должно хранить лишь `concept → (module, target)`, а проверка точного членства остаётся за каталогом (правило «pointer download требует точного членства» сохраняется). Установленный модуль несёт собственный `concept-delta` (имена+связи его документов, десятки KB), при монтировании сливается в in-memory trie без релиза ядра; поиск = имена ядра ∪ FTS установленных модулей. Что уходит из ядра: `canonicalDefinition` (7.4 MB), `knowledge_evidence`, `knowledge_facts`, ICD-путь — в пак определений/справки или в микро-пак превью (0.93 MB zstd). Это противоречит ADR 0017 в части «короткий pointer-текст в ядре» → нужен ADR.

## 6. Что не измерено и почему

- Любое время/память на Android/WebView и HyperOS (нет устройства; прокси — Node/V8 на хосте).
- Двойное хранение IDB+OPFS и сиротские OPFS-копии — по коду, без запуска приложения.
- Блочно-сжатый VFS: нет реализации; ратио по сэмплу блоков (каждый 4-й/8-й), клинреки по одному файлу, время холодного запроса — расчёт.
- Aho–Corasick в WASM: не строился (не нужен при границах слов); OCR-страницы пользователя: нет образцов.
- Размер декодер-only WASM zstd со словарём: нет Emscripten; измерен `@bokuweb/zstd-wasm` 252 KB (с компрессором).
- Влияние метрик качества поиска на реальном корпусе: проверена идентичность top-50 bm25 (160 запросов), но не `benchmark:*`.
- Нативная (KMP) ветка заморожена и не аудитировалась; затронутые пути проверялись только по WebView/Capacitor-коду.
