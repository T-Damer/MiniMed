# Q1 — Датасеты запросов и бенчмарк поиска по полным базам (2026-10-02)

Задача STATE Q1: у владельца нет собственного журнала запросов; нужен реалистичный
retrieval-бенчмарк на готовых датасетах (русских или переводимых), чтобы заменить синтетический
педиатрический набор из [embeddings-kr-2026-10-02.md](embeddings-kr-2026-10-02.md) (слабые подстрочные метки,
только КР). Результат: исследование источников, набор из 500 запросов с относительностью на уровне
документов, загрузчик/скорер, базовый уровень лексического поиска приложения.

**Метки достоверности.** ✔ — я сам запросил первичный источник 2026-10-02 (API/страница/файл) и читал
ответ; ◐ — через WebFetch-пересказ или поисковую выдачу; ○ — из памяти/вторичных источников, не перепроверено.

Итог: **родной русский источник с настоящей клинической речью и кодами МКБ — это RuMedPrimeData (жалобы) и RuCCoD
(диагнозы)**; оба под CC BY. Для запросов про лекарства единственный найденный крупный источник — форум
`blinoff/medical_qa_ru_data` без лицензии, поэтому он остаётся локальным. Перевод не потребовался; в наборе нет
машинно-переведённых строк (поле `machineTranslated` везде `false`, оно есть на случай будущих переводов).

Известные ограничения источников:

- RuMedPrime — приёмы одной поликлиники (неврология, эндокринология, гинекология, терапия): темы перекошены; жалобы
  записаны врачом (не поисковые запросы пациента); метка — диагноз врача, а не «правильный документ».
- RuCCoD — фразы выделены из заключений (в `.ann` встречаются обрывки вроде «болевым» и повторяющиеся идентификаторы
  сущностей); метки приведены к МКБ-10 по правилам аннотаторов (в статье указана МКБ-10-КМ, но коды русской МКБ-10
  вида `N70.9`, `M54.4` совпадают с нашим справочником).
- Форум — вопросы пациентов, не врачей; метка выводится из названия препарата, т.е. проверяет узнавание названия
  в шумной речи, а не клиническое попадание.

## 2. Бенчмарк

Файлы:

- `tools/benchmarks/retrieval-icd-queries.json` — **400 запросов**, под CC BY (RuMedPrime 3.0, RuCCoD 4.0): можно
  хранить в репозитории с указанием авторства (в файле: `sources[].attribution`, контрольные суммы источников).
- `data/build/retrieval-drug-forum-queries.json` — **100 запросов про лекарства**, **в git не попадает** (`data/build/*`
  игнорируется): лицензия набора неизвестна. Пересоздаётся скриптом из скачанного источника.
- `tools/benchmarks/src/retrieval-benchmark.ts` (+ `.test.ts`) — загрузчик с валидацией, сопоставление кодов МКБ,
  метрики; `build-retrieval-benchmark.ts` — построение; `run-retrieval-benchmark.ts` — прогон по движку приложения.

```bash
bun tools/benchmarks/src/build-retrieval-benchmark.ts --fetch   # скачать источники в data/raw/query-datasets (≈25 МБ) и собрать
bun tools/benchmarks/src/build-retrieval-benchmark.ts           # пересобрать из скачанного
bun tools/benchmarks/src/run-retrieval-benchmark.ts --path=app --split=dev    # прогон; тест — только для отчёта
```

Состав (по 100 на источник и сплит; в каждом сплите ровно по 70 запросов, у которых есть соответствующая КР,
и 30 — только с карточкой МКБ):

| Источник | Стиль | dev | test | Сплит из источника |
| --- | --- | ---: | ---: | --- |
| RuMedPrimeData | `complaint`: жалобы врачом на приёме (25–400 знаков, медиана ≈100) | 100 | 100 | официальные dev/test RuMedTop3 (по `new_event_id`) |
| RuCCoD | `diagnosis-phrase`: формулировка диагноза (медиана 22 знака) | 100 | 100 | train → dev, test → test; фраза из dev, встречающаяся в test, исключена |
| форум (локально) | `drug-question-title` (заголовок темы, 50) и `drug-question-text` (≤300 знаков текста, 50) | 50 | 50 | хэш id записи |

Выбор строк детерминирован (порядок SHA-1 от id записи, соль `minimed-retrieval-2026-10-02`), не более 4 строк на
трёхзнаковый блок МКБ в сплите (иначе M54 съедает набор), без повторов текста; для RuMedPrime отброшены жалобы короче 25
и длиннее 400 знаков, строки с масками анонимизации (`*ДАТА*`) и «жалоб нет». Для RuCCoD отброшены фразы короче 5 знаков,
одиночные прилагательные-обрывки и фразы с несколькими разными кодами.

### Как выводится относительность

База сопоставления — **реальные полные базы на 2026-10-02**: 753 модуля КР (`data/build/release-clinical` + 30 новых
редакций `data/build/core-clinical-new-editions`) с кодами МКБ из снимка реестра Минздрава
`data/raw/official-clinical-registry/2026-10-02` (763 действующих + все статусы), 9 549 карточек МКБ `rls.mkb.node.*`
из `mkb.db`, плюс прежнее ядро `core.db`, `medications.db`, `ambulatory.db`, `regulatory.db`, `reference.db`.

Для ICD-строк (код источника → `goldCodes`):

- **grade 3**: КР, у которой в реестре есть тот же код, родитель или потомок (`K29` покрывает `K29.5`; диапазон `C00-C14`
  покрывает `C02.1`), и карточка МКБ того же/родительского/дочернего кода;
- **grade 1**: другой код того же трёхзнакового блока (КР или карточка-«сестра»);
- в строку попадают только коды, у которых есть хотя бы одна grade-3 карточка (код валиден в нашей МКБ).

Для строк про лекарства (`goldNames`): в тексте найдено ровно одно зарегистрированное название (торговое или МНН, по
таблице алиасов `core.db`, с учётом падежных окончаний ≤3 знаков) → **grade 3**: документ `esklp.mnn.<МНН>` и Allmed-инструкции с
тем же названием (`drug.allmed.*`). Названия, указывающие на несколько продуктов, отброшены, как и слова
обычной речи, совпавшие с реестром (список в `NOT_A_DRUG_NAME`: «инфекции», «миндалин», «кальций», гормоны-анализы и т.п.,
составлен просмотром 120 самых частых совпадений).

Что относительность **не** говорит: КР того же кода не обязательно содержит нужный фрагмент — оценка на уровне
документа; диагноз, поставленный врачом, может расходиться с «лучшим» документом для жалобы (поэтому доля строк с КР
ограничена 70 % и отдельно считается `anyR@5` по grade 1).

### Метрики

Глубина 20 групп документов. Документ считается один раз (указатель ядра приравнен к целевому документу).
`R@k` — доля запросов, у которых в топ-k есть документ grade 3; `MRR@10`; `nDCG@10` с усилениями 3 и 1; `anyR@5` —
grade 1 тоже засчитывается. Отдельно: «КР only» (запросы, у которых есть grade-3 КР; нужно найти именно КР) и
«МКБ card only».

## 3. Базовый уровень (лексический поиск приложения)

Прогон 2026-10-02, 500 запросов (оба сплита), движок приложения (`MedicalCore` над `core.db` 0.6.47 + все компаньоны +
753 модуля КР), `PortableHashEmbedder` как у остальных бенчмарков, т.е. семантики нет. Два пути: `core` — гибридный поиск
без области; `app` — как в приложении (область «Диагностика» + клинический разбор для ICD-строк, область «Лекарства» +
lookup для вопросов о лекарствах).

Метрика «любой grade-3 документ» (КР, карточка МКБ или лекарство), глубина 20, сплиты dev/test; test показан для отчёта,
**не для подгонки**. Хост: Apple Silicon, под нагрузкой других процессов (латентность справочная: p50 5,5 с / p95 17 с для
`app`, 4,1 / 18,9 с для `core` на 753 смонтированных модулях КР; длинные жалобы дольше).

Что видно:

- **Жалобы почти не находят ничего** (R@5 ≈ 0.05 на обоих путях): длинная лексическая жалоба из нескольких симптомов
  («головная боль, озноб, насморк, … слабость») возвращает препараты от простуды и разделы учебников, а не ОРВИ или МКБ
  `J00`. Это ровно тот пробел, который должен закрывать поиск по смыслу (E1); на синтетических педиатрических запросах
  со слабыми подстрочными метками лексика выглядела лучше (R@5 0.30).
- **Диагнозы-фразы:** путь `core` лучше в R@5 (0.405 против 0.220), потому что `app` («Клинический разбор») не ставит
  карточки МКБ на первые места (МКБ-only R@1 = 0.000 на `app`), зато точнее по КР (R@1 КР 0.171 против 0.036). Разрыв
  dev/test велик (RuCCoD `core` R@5 0.31 против 0.50) — на 100 запросах доверительный интервал ≈ ±0.09, выводы по одному
  сплиту делать нельзя.
- **Лекарства:** узнавание названия работает (R@5 0.87 на `app`), но только 0.36 в топ-1 из-за нескольких документов-близнецов
  (инструкции Allmed, МНН, комбинации); путь `core` без области выше по R@1 (0.48), ниже по R@5.
- Потолок глубины: `app` отдаёт для КР не более ≈10 групп (R@20 = R@10 по КР-only), т.е. «КР только» не растёт после 10.

Отчёты прогона (по запросам, топ-5, оценки) лежат в `data/build/retrieval-benchmark-{app,core}-all.json` (не в git).
Основная выводимая цифра для сравнения вариантов поиска: `all`, путь `app`, **dev** — R@5 0.272, MRR@10 0.200, nDCG@10 0.182
(test: 0.292 / 0.217 / 0.194).


## 4. Что дальше

- Ставить E1 (сравнение embedding-моделей) на этом наборе вместо синтетического: `tools/benchmarks/src/export-retrieval-candidates.ts`
  принимает JSONL с `query_id`/`query` — достаточно выгрузить строки набора.
- Набор не заменяет запросы врачей: доли — жалобы амбулаторных приёмов, диагнозы и вопросы пациентов. Когда появятся
  настоящие запросы владельца, их стоит добавить отдельным источником (`source`) в тот же формат.
- Контроль качества меток: выборочно просмотрите ≈30 строк `forum-drug` (название найдено верно?) и ≈30 строк RuMedPrime
  (диагноз врача ↔ жалоба правдоподобны?); при необходимости дополните `NOT_A_DRUG_NAME`.
- Соблюдение лицензий: при публикации репозитория сохранять `sources[].attribution`; для RuCCoD лицензия заявлена только в
  статье — при сомнениях заменить строки RuCCoD на RuMedPrime.
